# RuleBench: Rule-Interaction Sensitivity in LLM-Generated SQL

An execution-grounded research benchmark for evaluating how individual business rules, combined constraints, rule ordering, database schema complexity, and dataset size influence SQL generated by Large Language Models (LLMs).

## Research Objective

This project investigates whether custom business constraints influence the correctness and execution reliability of LLM-generated SQL queries.

The benchmark evaluates:

- Individual business-rule compliance.
- Combined business-rule compliance.
- Sensitivity to rule ordering.
- Sensitivity to database schema complexity.
- Effects of dataset size on generated SQL execution and compliance.

## Research Question

**How do individual and interacting business constraints affect the execution correctness and semantic compliance of LLM-generated SQL?**

The benchmark uses the following business question:

> Calculate the total reportable net revenue across all orders in the database.

**Common revenue definition:** net revenue is the sum of all `payments.amount` values minus the sum of all `refunds.amount` values. This definition applies to every experimental condition. Refund subtraction is therefore an evaluation invariant, not an experimental factor.

## Experimental Design

The experiment uses a full-factorial design.

| Factor                    | Values                    |
| ------------------------- | ------------------------- |
| Dataset sizes             | 100, 1,000, 10,000 orders |
| Schema profiles           | Baseline, Expanded        |
| Conditions                | 5                         |
| Trials per condition      | 10                        |
| Total planned generations | 300                       |

### Business-rule conditions

| Condition              | Experimental constraints |
| ---------------------- | ------------------------ |
| A_single_deleted_rule  | Exclude orders belonging to deleted customers |
| A_single_verified_rule | Include orders only from verified customers |
| A_single_join_rule     | Aggregate payments and refunds separately per order before joining to avoid join fan-out |
| B_combined_rules       | Apply all three experimental constraints in canonical order |
| C_reordered_rules      | Apply the same three experimental constraints in a different order |

Net revenue (payments minus refunds) is common to all five conditions and is not counted as an experimental constraint. The combined and reordered conditions contain exactly the same constraints; only their order differs.

### Schema profiles

**Baseline schema**

- customers
- orders
- order_items
- payments
- refunds

**Expanded schema**

- customers
- orders
- categories
- products
- order_items
- payment_methods
- payments
- refund_reasons
- refunds

The expanded schema introduces additional relationships and normalization.

## Installation

Clone the repository:

```bash
git clone https://github.com/sairajKhilariArch/rule-interference-benchmark.git

cd rule-interference-benchmark
```

Create a virtual environment:

```bash
python -m venv .venv
source .venv/bin/activate
```

Install dependencies:

```bash
pip install -r requirements.txt
```

## Configure the LLM API

The experiment runner currently expects an OpenAI-compatible API endpoint at:

```text
http://127.0.0.1:8645/v1
```

Start your compatible local proxy or inference service and ensure the configured model is available:

```text
upstage/solar-mini4:free
```

The endpoint and model configuration in the runner and experiment configuration must agree.

## Generate Synthetic Datasets

Generate the baseline datasets:

```bash
python database/generate_dataset.py --profile baseline
```

Generate the expanded datasets:

```bash
python database/generate_dataset.py --profile expanded
```

This creates six synthetic SQLite databases under:

```text
results/datasets/
```

The generator uses a deterministic seed by default. Existing dataset files are not overwritten.

## Run Experiments

Run a pilot experiment:

```bash
python src/experiment_runner.py --pilot
```

Run the complete experiment:

```bash
python src/experiment_runner.py
```

The full experiment plans 360 SQL generations.

### Resume an interrupted experiment

Use the run ID printed by the runner:

```bash
python src/experiment_runner.py --resume YOUR_RUN_ID
```

The runner uses checkpoints and validates the saved configuration before resuming.

## Run Analysis

After an experiment has completed, generate the descriptive analysis:

```bash
python src/analyze_run.py
```

Then run statistical analysis:

```bash
python src/statistical_analysis.py
```

The analysis includes:

- Condition-wise compliance metrics.
- SQL execution and result-contract failures.
- Canonical versus reordered rule comparisons.
- 95% Wilson confidence intervals.
- Exact McNemar tests for paired comparisons.
- Holm-Bonferroni multiple-comparison correction.

Generated reports are stored locally inside the corresponding experiment run directory.

## Run Tests

Execute the test suite:

```bash
python -m pytest -q
```

## Evaluation Principles

The benchmark separates different types of failure:

1. SQL execution failure.
2. Result-contract failure.
3. Evaluation failure.
4. Business-rule compliance failure.

A successfully executed SQL query is not automatically considered semantically correct.

The evaluator checks the query result against independently calculated reference values and tests the assigned business constraints.

## Reproducibility and Data Handling

- Experiment settings are maintained in a version-controlled configuration file.
- Synthetic datasets are generated using deterministic seeds.
- Experiment metadata records configuration snapshots and hashes.
- Interrupted runs can be resumed when checkpoint and configuration validation succeeds.
- Generated databases, SQL outputs, experiment logs, and result files are kept locally.
- The original research database is protected from accidental modification.

Do not publish private datasets, raw experiment outputs, credentials, or sensitive research materials.

## Limitations

- The current benchmark evaluates one configured model.
- Ten trials per condition provide limited statistical power.
- Results are specific to the tested prompts, model, schemas, and synthetic datasets.
- SQL execution success does not establish semantic correctness.
- Additional models, trials, and independent replications are needed before making broader generalizations.

## Research Scope

This repository currently implements an execution-grounded benchmark for SQL generation and business-rule interaction. It does not claim to evaluate general-purpose code generation.
